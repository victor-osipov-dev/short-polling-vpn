# Проектирование: балансировка, пользовательские маршруты и идентификация пользователей

Статус: черновик к обсуждению
Дата: 2026-11-13

## 1. Требования

1. Несколько серверов должны работать одновременно, без поломки TCP-сессий.
2. Пользователь сам задаёт маршрут запросов, например:
   - напрямую к иностранному серверу (round/random среди серверов);
   - через российский сервер, а оттуда — к иностранным (round/random);
   - через CDN (тот же российский сервер или другой), затем к иностранным или напрямую.
3. Сервер не должен заранее знать маршрут: информация о маршруте приходит в запросе.
4. Нужно различать пользователей и уметь отключать конкретного пользователя.
5. Стратегия выбора (round/random) должна применяться к списку кандидатов на нужном участке.

## 2. Термины

- **Node** — сервер с ID, адресами и ролью.
- **Entry** — узел, к которому подключается клиент.
- **Relay** — промежуточный узел.
- **Exit** — узел, который открывает соединение к целевому сайту и хранит состояние TCP-сессий.
- **Route** — упорядоченный список узлов: `[entry, relay..., exit]`.
- **Transport** — способ доставки HTTP до узла: `direct` или `cdn` (несколько CDN-URL).
- **Session affinity** — все кадры одной TCP-сессии идут в один и тот же exit.

Ключевая идея: **состояние сессий хранит только exit**. Entry/relay — stateless-форвардеры. Тогда смена entry/relay не рвёт сессии, а несколько серверов можно использовать одновременно.

## 3. Предлагаемая архитектура

### 3.1. Синхронная цепочка short-polling

Клиент отправляет poll на entry. Entry проверяет пользователя и маршрут, форвардит **тот же зашифрованный payload** следующему узлу и возвращает ответ. Каждый узел снимает себя из маршрута.

```
client ──poll──▶ entry (RU) ──poll──▶ exit (DE) ──TCP──▶ target
       ◀─resp──         ◀─resp──
```

- Entry и relay **не расшифровывают** payload: он зашифрован end-to-end до exit.
- Entry/relay не хранят состояние TCP-сессий — только пользователей, политики и адреса пиров.
- Exit расшифровывает кадры, ведёт сессии и буферы, открывает соединения к target.
- Ответ проходит обратно по цепочке как обычный HTTP-ответ.

Преимущества:

- Полностью соответствует short-polling (нет долгих соединений).
- Смена entry/relay между poll-ами безопасна: состояние на exit.
- Простая балансировка entry/relay: round/random допустим на каждый poll.
- Пользовательский маршрут явно передаётся в запросе.
- Entry не видит содержимое трафика.

Ограничения:

- Задержка складывается из RTT всех hop-ов.
- Нужны таймауты и deadline на всю цепочку.
- Нужны политики, чтобы relay не стал открытым прокси.

### 3.2. Маршрут в запросе

Payload остаётся зашифрованным, а маршрут должен быть читаем relay-ями. Поэтому маршрут кладётся в **подписанный конверт** рядом с payload:

```
body = b64u(route_envelope) "." b64u(blob)
```

`route_envelope` (JSON, подписан пользовательским ключом):

```json
{
  "v": 1,
  "user": "u_alice",
  "device": "phone-1",
  "ts": 1794594000,
  "hops": ["ru-1", "de-1"],
  "exit": "de-1",
  "nonce": "base64url"
}
```

Почему в body, а не в заголовках:

- многие CDN вырезают или кэшируют нестандартные заголовки;
- body CDN обычно передаёт как есть;
- проще сохранить совместимость с `poll_data_in: body`.

Для `poll_data_in: header` можно оставить вариант с заголовком, но CDN-режим рекомендуется только с body.

Подпись: HMAC или Ed25519 пользователя. Проверяют все узлы цепочки. Payload шифруется ключом, известным только клиенту и exit (например, HKDF от секрета пользователя с `info = "enc"`).

### 3.3. Резолвинг маршрута и стратегии

Рекомендуется: **клиент резолвит конкретную цепочку на сессию**.

Конфиг клиента:

```yaml
routes:
  - name: "RU → EU"
    hops:
      - candidates: ["ru-1"]
        transport: direct
      - candidates: ["de-1", "nl-1"]
        strategy: round
  - name: "CDN → RU → EU"
    hops:
      - candidates: ["ru-1"]
        transport: cdn
        cdn_urls: ["https://cdn1.example", "https://cdn2.example"]
      - candidates: ["de-1", "nl-1"]
        strategy: random
  - name: "Direct EU"
    hops:
      - candidates: ["de-1", "nl-1"]
        strategy: random
```

Алгоритм:

1. При создании SOCKS-сессии клиент выбирает по одному кандидату на hop согласно стратегии.
2. Полученная цепочка (`hops`) фиксируется за сессией.
3. Все кадры сессии всегда идут с этой цепочкой.
4. При падении entry/relay можно пересобрать только эти hop-ы, сохранив exit — сессии не рвутся.
5. При падении exit сессии сбрасываются (TCP невозможно перенести), приложение переподключается.

Альтернатива (если стратегию должен применять сервер): hop передаётся как список кандидатов, entry выбирает next hop и фиксирует выбор в подписанном ответе/токене. Это сложнее и требует состояния или подписи решения. По умолчанию предлагаю клиентский резолвинг.

### 3.4. Identity и отключение пользователей

Стабильная идентификация:

- `user_id` — логический пользователь;
- `device_id` — конкретное устройство/установка;
- `user_secret` — секрет для HMAC/подписи и вывода ключей.

Реестр на каждом узле:

```yaml
users:
  - id: u_alice
    name: "Alice"
    enabled: true
    secret_hash: "..."
    allowed_hops: ["ru-1", "de-1", "nl-1"]
    allowed_exits: ["de-1", "nl-1"]
    max_hops: 2
    max_sessions: 200
```

Запрос:

- содержит `user_id`, `device_id`, `ts`, `nonce`, `hops`, подпись;
- узел проверяет: пользователь существует, `enabled`, подпись, окно времени, nonce, допустимость маршрута;
- отключённый пользователь получает обычный fake-ответ (маскировка), трафик не проходит.

Управление:

- CLI `manage.py user add|disable|enable|list|rotate-secret`;
- либо админ-API/панель (обсуждается);
- в клиенте — профиль с `user_id` + секретом (ввод вручную/QR/файл).

Backward compatibility:

- текущий общий PSK оформляется как пользователь `default`;
- старые клиенты без `X-Proto: 3` продолжают работать;
- новых пользователей можно переводить постепенно.

### 3.5. Реестр узлов и адресация

- Узлы адресуются по `node_id`, а не по произвольному URL.
- Каждый узел хранит локальный `peers` (id → URL), чтобы relay не мог сходить на произвольный адрес (защита от SSRF/открытого прокси).
- Клиент получает каталог узлов (вручную или подписанным конфигом).
- Для CDN узел может иметь несколько `cdn_urls`; клиент выбирает их по стратегии, но помнит, что все они ведут на один `node_id`.

### 3.6. Обработка ошибок и failover

- Ошибка entry/relay: клиент пробует другой узел на этом hop; exit и сессии сохраняются.
- Ошибка exit: сбросить сессии, использующие этот exit; новые сессии — на другой exit.
- Таймауты: общий deadline на цепочку; каждый hop уменьшает оставшееся время.
- Потеря кадров: очереди отправляются только после успешного ответа либо при ошибке сессия принудительно закрывается, чтобы приложение переподключилось. Нужно выбрать политику (см. вопросы).
- Карантин: на уровне узла/URL, с backoff; не сбрасывать все карантины при полном отказе.
- Health-check: лёгкий запрос к entry/exit (например, `/healthz` с подписью), чтобы не ждать таймаутов.

### 3.7. Защита

- Подпись конверта пользователем; payload — end-to-end до exit.
- Проверка `allowed_hops`/`allowed_exits` на каждом узле.
- Запрет произвольных URL в маршруте (только `node_id` из `peers`).
- Лимит hop-ов и размера конверта.
- Anti-replay: окно времени + LRU nonce на пользователя.
- Ограничение сессий/трафика на пользователя (опционально).
- Логи без payload; user_id можно хэшировать в логах, если нужно.
- Relay не логирует URL target (он его и не видит).

## 4. Примеры маршрутов

### Напрямую к иностранным серверам

```
client ──▶ de-1 (exit) ──▶ target
```
`hops: ["de-1"]`, стратегия random по `["de-1","nl-1"]`.

### Через российский сервер к иностранным

```
client ──▶ ru-1 (relay) ──▶ de-1 (exit) ──▶ target
```
`hops: ["ru-1","de-1"]`, exit выбирается random.

### Через CDN, затем к иностранным

```
client ──▶ CDN ──▶ ru-1 (relay) ──▶ de-1 (exit) ──▶ target
```
`hops: ["ru-1","de-1"]`, `transport: cdn`, `cdn_urls` для ru-1.

### CDN напрямую к иностранному exit

```
client ──▶ CDN ──▶ de-1 (exit) ──▶ target
```
`hops: ["de-1"]`, `transport: cdn`.

## 5. Изменения протокола

Новая версия `X-Proto: 3` / `PROTO_VERSION = "3"`:

- `body = route_envelope + "." + blob` (base64url);
- `route_envelope`: `{v, user, device, ts, nonce, hops, exit}` + подпись;
- `blob` шифруется ключом пользователя end-to-end до exit;
- `X-Proto: 2` остаётся для обратной совместимости;
- ответы exit не меняются (stream records), relay возвращает их как есть;
- заголовки ответа: `Cache-Control: no-store`.

## 6. Изменения клиента

1. **Session affinity**: у каждой сессии есть `route` (конкретные hop-ы).
2. **Poll-группировка**: кадры группируются по паре `(transport_url, route)`; на каждую группу — отдельный poll.
3. **Несколько poll-циклов**: активные entry/transport опрашиваются параллельно или последовательно; ответы сливаются.
4. **Планировщик маршрутов**: выбор кандидатов по стратегии, фиксация на сессию, пересборка при ошибках.
5. **Управление пользователем**: `user_id`, `device_id`, секрет; экран настроек.
6. **UI маршрутов**: конструктор hop-ов и стратегий, предпросмотр цепочки.
7. **Failover**: переключение entry/relay без сброса exit-сессий; сброс при смене exit.
8. **Потеря кадров**: не удалять из очередей до успешной отправки; при неоднозначной ошибке — закрывать сессию, чтобы приложение переподключилось.

## 7. Изменения сервера

1. **Node identity**: `node_id`, роли, `peers`, `cdn_urls`.
2. **User registry**: пользователи, флаги, права, лимиты.
3. **Route validation**: проверка прав и допустимых hop-ов.
4. **Relay**: HTTP-клиент к следующему узлу, проброс payload, таймауты, keepalive-пул.
5. **Exit**: текущая логика сессий/буферов.
6. **Admin**: CLI/API для пользователей и узлов.
7. **Health endpoint**.
8. **Метрики**: запросы, ошибки, карантины, активные сессии по пользователям.

## 8. Этапы внедрения

### Этап 0 — исправление явных ошибок (сделано)

- перевзвод карантина;
- один счётчик ошибок на HTTP-ошибку;
- отсутствие сброса всех карантинов;
- ожидание истечения карантина вместо ретрай-шторма;
- отсутствие ложного «URL recovered».

### Этап 1 — per-session affinity (сделано)

- сессия закреплена за entry/exit (`ClientSession.server_base`);
- кадры группируются по URL, на каждый URL — отдельный poll;
- все доступные URL опрашиваются каждый цикл для сбора буферизованных ответов;
- отдельное смещение времени на каждый URL;
- корректный failover: закрываются только сессии упавшего URL;
- это уже чинит одновременную работу нескольких серверов (проверено: 8/8 на двух серверах, 0 предупреждений `DATA not found`).

### Этап 2 — идентификация пользователей

- `user_id`/`device_id`, подпись, реестр;
- отключение пользователя;
- legacy PSK как `default`;
- CLI управления.

### Этап 3 — маршруты и relay

- конверт маршрута;
- валидация и форвардинг;
- direct/1 relay/2 relay;
- failover entry/relay с сохранением exit.

### Этап 4 — CDN

- транспорт через CDN;
- проверка, что CDN не режет body/заголовки;
- no-store, обход кэша;
- несколько CDN-URL на один node_id.

### Этап 5 — UI и админка

- конструктор маршрутов;
- статус узлов и карантинов;
- управление пользователями;
- статистика.

## 9. Открытые вопросы

1. **Кто применяет стратегию** на каждом hop: клиент (рекомендую) или сервер?
2. **Гранулярность маршрута**: профиль целиком, приложение, домен/назначение? Нужны ли правила «этот сайт — напрямую, этот — через RU»?
3. **Приватность**: должен ли entry видеть `user_id` и маршрут? Или нужны анонимные токены, чтобы даже entry не знал пользователя?
4. **Максимум hop-ов** и разрешённые топологии: только entry→exit или цепочки длиннее?
5. **Каталог узлов**: ручной конфиг на каждом узле, центральный подписанный каталог, или API discovery?
6. **Идентификация**: один пользователь = много устройств? Один секрет на устройство? Как выдавать секреты (вручную/QR/файл)?
7. **Админка**: CLI, web-панель, Telegram-бот? Где хранить реестр — YAML на узлах или общая БД?
8. **Backward compatibility**: оставляем ли текущий общий PSK как `default` и на какой срок?
9. **Политика при падении exit**: сбрасывать сессии (единственный вариант для TCP) — согласны?
10. **Потеря кадров**: при неоднозначной ошибке (таймаут после отправки) закрывать сессию или пытаться переотправить?
11. **CDN**: какие CDN используются, проходят ли POST-body и не кэшируют ли ответы? Нужно протестировать на конкретном провайдере.
12. **DNS**: гнать DNS через exit, через entry или решать локально?
13. **Квоты и биллинг**: нужны ли лимиты трафика/сессий на пользователя?
14. **Порты/связность**: могут ли узлы ходить друг к другу по 443/8443? Есть ли NAT?
15. **Все ли узлы — этот же софт**? Нужен ли установщик для новых узлов?
16. **UI**: где редактировать маршруты — Android, desktop, оба? Должен ли пользователь менять маршрут на лету?

## 10. Рекомендуемые значения по умолчанию

- Стратегию применяет клиент.
- Маршрут задаётся на профиль; позже — per-app.
- Payload E2E-шифруется до exit; entry/relay видят только `user_id` и hop-ы.
- Максимум 3 hop-а.
- Узлы адресуются по `node_id`; URL — из локального `peers`.
- Legacy PSK — пользователь `default`, отключаемый.
- При ошибке exit — сброс сессий; при ошибке entry/relay — переключение без сброса.
- CDN-режим — только POST + body-конверт + `Cache-Control: no-store`.
