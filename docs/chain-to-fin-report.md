# Отчёт: маршрут `chain to fin` (09e1f1e2-16a5-4293-9dee-f445d4818045)

Дата: 2026-11-14

> **Статус после исправления (вариант C):** клиент больше не строит цепочки
> с повторяющимися узлами. Для текущего маршрута он выдаёт
> `ru-2 → de-1`, `de-1 → fi-1`, `fi-1 → ru-2` и т.д. Панель показывает
> предупреждение, а заведомо невозможные маршруты не сохраняет. Раздел
> «Исправление» в конце документа.

## Кратко (до исправления)

Маршрут **не работает в текущем виде**. Оба hop-а содержат один и тот же
список кандидатов `[ru-2, de-1, fi-1]` со стратегией `round`. Round-robin
выбирает кандидата независимо для каждого hop-а, но с одинаковым индексом,
поэтому клиент всегда формирует цепочку из **двух одинаковых узлов**:

```
ru-2 -> ru-2
de-1 -> de-1
fi-1 -> fi-1
```

Сервер отвергает маршрут с повторяющимся node_id (`_parse_route`), отвечает
маскировочным `200` с `Content-Type: application/javascript` (или другим по
расширению), клиент считает это ошибкой и закрывает сессию. В итоге non-RU
трафик через профиль `chain to fin` не проходит.

## 1. Что задано

```
route id:  09e1f1e2-16a5-4293-9dee-f445d4818045
name:      chain to fin
hops:
  - candidates: [ru-2, de-1, fi-1], strategy: round
  - candidates: [ru-2, de-1, fi-1], strategy: round
```

Профиль `chain to fin` использует этот маршрут для `non_ru`:

```
route_ru:      RU exit
route_non_ru:  chain to fin
route_private: direct
```

## 2. Как маршрут проходит по этапам

### 2.1. Подписка

`/sub/<token>` отдаёт каталог `routes` и `client_profiles`. Клиент получает
маршрут как список hop-ов; каждый hop — список кандидатов и стратегия.

### 2.2. Выбор маршрута в SplitRouter

`split_routing.py` для каждого hop-а вызывает `_pick_pair`:

```python
for i, hop in enumerate(hops):
    strategy = hop.get("strategy", "round")
    resolved.append(self._pick_pair(f"{route_name}:{i}", candidates, strategy, available))
```

Для `round` используется отдельный счётчик на ключ `route:hop_index`:

```python
idx = self._rr.get(key, 0)
self._rr[key] = idx + 1
return pool[idx % len(pool)]
```

Оба hop-а имеют одинаковый список и одинаковую длину. Счётчики
`chain to fin:0` и `chain to fin:1` стартуют с нуля и увеличиваются
синхронно, поэтому индексы всегда совпадают.

### 2.3. Формирование цепочки

`route_for()` возвращает:

```
mode=tunnel, entry_url, route_ids=(entry_id, exit_id), category=non_ru
```

Для текущего маршрута:

| Запрос | hop 0 | hop 1 | route_ids | Результат |
|---|---|---|---|---|
| 1 | ru-2 | ru-2 | `ru-2,ru-2` | ошибка |
| 2 | de-1 | de-1 | `de-1,de-1` | ошибка |
| 3 | fi-1 | fi-1 | `fi-1,fi-1` | ошибка |
| 4 | ru-2 | ru-2 | `ru-2,ru-2` | ошибка |

### 2.4. Отправка на entry

Клиент закрепляет сессию за entry URL и передаёт `X-Route: ru-2,ru-2`
(или другой self-pair). HMAC считается по этой строке, поэтому подпись
корректна; проблема не в подписи.

### 2.5. Проверка на сервере

`server.py::_parse_route`:

```python
route = [part.strip() for part in raw.split(",") if part.strip()]
if len(route) > 3 or len(set(route)) != len(route):
    return []
```

Для `ru-2,ru-2`, `de-1,de-1`, `fi-1,fi-1` возвращается пустой список.
Сервер отвечает `fake_response(request)` — маскировочный `200` с типом
по расширению пути (JS/CSS/JSON/картинка). Настоящий exit при этом не
вызывается.

### 2.6. Реакция клиента

Клиент ожидает `application/octet-stream`. Получает, например,
`application/javascript`. В логе:

```
unexpected response from https://... (application/javascript; charset=utf-8);
check user/device/route
closed 1 session(s) pinned to failed URL ...
```

Сессия закрывается, `curl` через SOCKS5 падает с TLS-handshake ошибкой
(соединение до цели не устанавливается).

## 3. Почему это не «просто две одинаковые ноды»

Даже если бы `_parse_route` пропускал дубли, relay-логика использует
`route.index(node_id)` — первое вхождение. Для цепочки с повторяющимся
узлом это даёт неоднозначность: сервер не может понять, на каком именно
месте цепочки он находится. В худшем случае получился бы цикл
`de-1 -> ru-2 -> de-1 -> ...`.

Сейчас дубли отсекаются раньше, поэтому цикла нет, но и трафика нет.

## 4. Локальное воспроизведение

Локально `SplitRouter` с текущим маршрутом:

```
1: entry=https://fimdi.ru:8443        route_ids=('ru-2', 'ru-2')
2: entry=https://2.27.37.211:8443     route_ids=('de-1', 'de-1')
3: entry=https://177.3.220.12:8443    route_ids=('fi-1', 'fi-1')
4: ... по кругу
```

С rotated-вариантом (второй hop сдвинут):

```
hop0 [ru-2, de-1, fi-1]
hop1 [de-1, fi-1, ru-2]

1: ru-2 -> de-1
2: de-1 -> fi-1
3: fi-1 -> ru-2
```

С Exit fixed:

```
hop0 [ru-2, de-1]   hop1 [fi-1]
1: ru-2 -> fi-1
2: de-1 -> fi-1
```

С `random` на обоих hop-ах вероятность self-pair для трёх кандидатов —
примерно `1/3` (в эксперименте 352 из 1000, 35.2%). То есть random здесь
тоже небезопасен.

Маршрут из 4 hop-ов обрезается до 3 с предупреждением:

```
route 'r' has 4 hops; max is 3, using first 3
```

## 5. Живые эксперименты

### 5.1. Текущий маршрут

Клиент с `route_non_ru = chain to fin`, SOCKS5, 6 запросов к `example.com`:

```
6 из 6 — ошибка (fake response / TLS handshake)
```

Сервер отбрасывает маршрут с дублем node_id. Без заголовка `X-Debug` он
отвечает маскировочным `200` (JS/CSS/JSON), поэтому клиент видит
`unexpected response`, а не `403`. При `X-Debug: 1` в логах видно причину:

```
177.3.220.12:   403 bad route: fi-1,fi-1
2.27.37.211:    403 bad route: de-1,de-1
157.228.134.211: 403 bad route: ru-2,ru-2
```

То есть каждый entry получал self-pair и отбрасывал его. Второй узел в
цепочке не вызывался.

### 5.2. Rotated-маршрут (рабочий)

```
hop0 [ru-2, de-1, fi-1]
hop1 [de-1, fi-1, ru-2]
```

6 запросов к `api.ipify.org`:

```
try 1: 2.27.37.211      (de-1)
try 2: 177.3.220.12     (fi-1)
try 3: 157.228.134.211  (ru-2)
try 4: 2.27.37.211
try 5: 177.3.220.12
try 6: 157.228.134.211
```

Все `200`. Цепочка каждый раз валидна, exit-ы меняются.

### 5.3. «В Финляндию через RU/DE»

```
hop0 [ru-2, de-1]
hop1 [fi-1]
```

6 запросов к `api.ipify.org`: все `200`, внешний IP всегда `177.3.220.12`
(fi-1). Entry чередуется между `ru-2` и `de-1`.

### 5.4. Явная трёхзвенная цепочка

```
ru-2 -> fi-1 -> de-1
```

4 запроса: все `200`, внешний IP `2.27.37.211` (de-1). Значит relay
работает и для трёх узлов, если node_id не повторяются.

### 5.5. Проверка на уровне HTTP без расшифровки

Для валидных цепочек (`ru-2,de-1`, `de-1,fi-1`, `fi-1,ru-2`,
`ru-2,de-1,fi-1`) сервер доходит до exit и отвечает `400 bad payload`
(ожидаемо: тестовый payload не является настоящим кадром). Для
self-pair (`ru-2,ru-2` и т.д.) — `200 application/javascript`, то есть
маршрут отброшен ещё до exit.

## 6. Выводы

1. Текущий `chain to fin` **нерабочий** из-за одинаковых hop-ов.
2. Проблема системная: `SplitRouter` не запрещает выбирать один и тот же
   узел на разных hop-ах, а `server._parse_route` запрещает дубли.
3. `random` не спасает: примерно треть запросов всё равно даёт self-pair.
4. Профиль `chain to fin` использует этот маршрут для `non_ru`, поэтому
   при его выборе non-RU сайты не открываются. RU-трафик и private при
   этом работают.

## 7. Как исправить

### Вариант A (рекомендую) — «в Финляндию»

```
hop0: [ru-2, de-1]   strategy: round
hop1: [fi-1]         strategy: round
```

Плюсы: всегда exit `fi-1`, entry чередуется, дублей нет.
Минусы: exit не балансируется (но по названию маршрута это и не нужно).

### Вариант B — балансировать все три узла

Сдвинуть кандидатов второго hop-а:

```
hop0: [ru-2, de-1, fi-1]
hop1: [de-1, fi-1, ru-2]
```

Плюсы: три валидные пары, round-robin по всем.
Минусы: exit зависит от entry; `fi-1` не всегда финишный.

### Вариант C — оставить как есть, но чинить код

Добавить в `SplitRouter` запрет на повтор node_id в цепочке (для
`round` — пропускать занятые узлы, для `random` — пересэмплировать).
Это более универсально, но меняет поведение всех маршрутов и требует
отдельных тестов.

## 8. Проверочные материалы

- Локальная симуляция: `SplitRouter` с текущим/rotated/fixed вариантами.
- Живые клиенты: SOCKS5 + `curl` через `example.com` и `api.ipify.org`.
- Серверные логи: `403 bad route: <node>,<node>` на всех трёх мастерах.
- HTTP-проба без расшифровки: self-pair → fake 200, валидная цепочка →
  `400 bad payload` уже на exit.

## 9. Что не менялось

Маршрут и профиль в БД не изменялись — отчёт фиксирует текущее поведение.
Рабочие тестовые конфиги были временными и удалены.

## 10. Исправление реализовано (вариант C)

В `split_routing.py` добавлен выбор цепочки целиком:

- DFS с возвратом: если кандидат на текущем hop-е занят или мешает
  следующему, выбирается следующий;
- запрещены повторы как по `node_id`, так и по URL (защита от разных ID
  на одном сервере);
- `round` сохраняет счётчики на `route:hop`, `random` перемешивает
  кандидатов;
- если уникальных доступных узлов меньше числа hop-ов, используется самый
  длинный валидный префикс и пишется `warning`;
- если цепочку нельзя собрать вообще, `route_for()` возвращает режим
  `error`, клиент пишет ошибку и отвечает SOCKS5 `general failure`,
 а не молча уходит на случайный сервер;
- при старте клиента проблемные маршруты логируются явно.

Панель (`/routes`) теперь:

- показывает статус `ок` / `предупреждение` / `ошибка`;
- не сохраняет маршрут, если уникальных узлов меньше числа hop-ов, есть
  неизвестный node_id или hop без кандидатов;
- показывает предупреждения о пересечении кандидатов и одинаковых URL;
- сохраняет валидные маршруты с пересечением кандидатов и выводит
  предупреждение на странице редактирования.

Сервер в `X-Debug`-логе пишет точную причину отказа:
`duplicate node_id in route`, `too many hops`, `invalid node_id`.

Живая проверка после обновления: 8 из 8 запросов через `chain to fin`
успешны, внешние IP циклически меняются:
`2.27.37.211 → 177.3.220.12 → 157.228.134.211`.

Если для `chain to fin` нужен **всегда финский exit**, этого вариант C не
делает: он лишь гарантирует валидную цепочку. Для «всегда FI» используйте
вариант A из раздела 7 (`[ru-2, de-1] → [fi-1]`).
