# Выбор URL и маршрутов: клиент vs админка

Дата: 2026-11-14

## 1. Коротко

В системе есть **три независимых механизма**, которые часто путают между собой:

1. **`URL select` в Android-клиенте** (`round` / `random`) — выбор базового URL
   только как fallback: когда маршрут не задан, split-routing выключен или
   нужен URL для служебного DNS-кадра.
2. **Стратегия каждого hop-а в админке** (`round` / `random`) — выбор узла
   внутри конкретного hop-а маршрута. Это и есть реальный выбор entry/relay/exit,
   если маршрут активен.
3. **Фоновый poll-фан-аут** — клиент каждый цикл опрашивает **все доступные
   URL**, даже если сессия закреплена за одним из них.

Прямого конфликта «первый hop vs клиентский round/random» нет: если маршрут
активен, entry берётся из hop #1, а клиентский `server_selector` для этой
сессии не используется. Но есть важные нюансы:

- на текущих маршрутах в админке у каждого hop-а **ровно один кандидат**,
  поэтому `round`/`random` в админке сейчас **не влияет ни на что**;
- клиентский `URL select` при активном split-routing тоже почти не влияет
  на целевой трафик;
- профиль с `split_enabled = false` игнорирует `route_non_ru` и уходит в
  обычный выбор URL клиентом;
- у профилей со включённым split-routing целевой трафик использует
  **не более двух серверов**, третий видит в основном фоновые poll-запросы;
- чтобы реально распределять целевой трафик по всем трём серверам, нужны
  маршруты с несколькими кандидатами в hop-ах (и желательно `random`).

## 2. Три уровня выбора

### 2.1. Android: `URL select` (`server_selector`)

Где: `ProxyConfig.serverSelector`, UI — Settings → Connection → `URL select`.

Что делает `_pick_server_base()`:

- `round` — выбирает URL из `server_urls` по кругу (`_rr_index`);
- `random` — `random.choice`;
- карантинные URL исключаются.

Когда используется:

- при создании SOCKS-сессии, если `route_for()` вернул `entry_url = None`
  (split-routing выключен, для категории не задан маршрут);
- для служебных DNS-кадров (`_dns_outbox`), если включён DNS relay.

Когда **не** используется:

- если маршрут активен, `register_session` получает `server_base` из hop #1
  и клиентский selector игнорируется;
- для фоновых пустых poll-запросов: они идут на все доступные URL, а не
  на один выбранный.

Значения по умолчанию:

- Android `ProxyConfig.serverSelector = "round"`;
- desktop `tunnel.py`, если ключ отсутствует, исторически использует
  `"random"`.

То есть при пустом/старом конфиге Android и desktop могут вести себя
по-разному.

### 2.2. Админка: стратегия hop-а

Маршрут хранится как список hop-ов:

```json
[
  {"candidates": ["ru-2", "de-1", "fi-1"], "strategy": "round"},
  {"candidates": ["de-1", "fi-1", "ru-2"], "strategy": "random"}
]
```

`SplitRouter._pick_chain()`:

- строит пул кандидатов для каждого hop-а;
- фильтрует по доступным URL;
- выбирает цепочку целиком;
- запрещает повтор `node_id`/URL;
- `round` — сдвигает счётчик на каждый успешный выбор;
- `random` — перемешивает кандидатов на каждом hop-е;
- если цепочку нужной длины собрать нельзя, сокращает её и пишет warning.

Первый hop — это entry, последний — exit. Именно эти значения попадают
в `server_base` сессии и в `X-Route`.

**Стратегия hop-а имеет смысл только если в hop-е больше одного
кандидата.** Если кандидат один, `round` и `random` дают один и тот же
результат.

### 2.3. Фоновый poll-фан-аут

`_poll_once()` в `tunnel.py` и Android `proxy_engine.py`:

```python
available = set(self._available_urls())
for base in available:
    groups.setdefault((base, ()), [])
```

То есть каждый цикл создаётся отдельный poll-запрос к **каждому**
доступному URL, даже если там нет сессий. Это:

- маскирует активный entry: все три сервера видят регулярные запросы;
- но не распределяет целевой трафик: он всё равно идёт через выбранный
  маршрут;
- создаёт довольно регулярный поток (см. раздел 7).

## 3. Матрица приоритетов

| Ситуация | Кто выбирает entry | Влияет ли `URL select` клиента |
|---|---|---|
| Split-routing включён, маршрут для категории задан | hop #1 маршрута | Нет |
| Split-routing включён, но для категории нет маршрута | клиентский `server_selector` | Да |
| Split-routing выключен (`routingEnabled=false`) | клиентский `server_selector` | Да |
| Маршрут задан, но собрать цепочку нельзя | соединение отклоняется (`error`) | Нет |
| DNS relay включён | `_pick_server_base()` | Да |
| Фоновый пустой poll | все доступные URL | Нет |

Вывод: это не конкурирующие настройки, а разные режимы. Конфликта
«первый hop против клиента» нет, но есть **неочевидный приоритет** и
«мёртвые» настройки.

Отдельно: `serverSelector` хранится в `ProxyConfig` профиля, но при импорте
подписки новые профили наследуют значение из базового/активного профиля —
отдельного поля в админке для него нет. Переключение `Round/Random` в
Settings меняет fallback-поведение активного профиля.

Пример:

```
маршрут: hop1 = [fi-1, de-1] random, hop2 = [ru-2]
клиент:  URL select = round
```

Для `ya.ru` entry всегда выбирается из `[fi-1, de-1]` по стратегии hop-а
`random`; клиентский `round` не участвует. Если бы для `ya.ru` маршрут не
был задан, entry выбирался бы по клиентскому `round` из всех `server_urls`.

## 4. Что сейчас в живой подписке

На момент проверки в `/sub` было 5 маршрутов, у всех hop-ов по одному
кандидату:

| Маршрут | Hop 1 | Hop 2 |
|---|---|---|
| `RU exit` | `ru-2` | — |
| `FI exit` | `fi-1` | — |
| `DE exit` | `de-1` | — |
| `RU -> DE` | `ru-2` | `de-1` |
| `FI -> DE` | `fi-1` | `de-1` |

Профили:

| Профиль | RU | non-RU | private | Целевые серверы |
|---|---|---|---|---|
| `RU direct -> DE direct` | `RU exit` | `DE exit` | direct | `ru-2`, `de-1` |
| `FI direct -> DE direct` | `FI exit` | `DE exit` | direct | `fi-1`, `de-1` |
| `RU -> DE relay` | `RU -> DE` | `RU -> DE` | direct | `ru-2`, `de-1` |
| `FI -> DE relay` | `FI -> DE` | `FI -> DE` | direct | `fi-1`, `de-1` |
| `DE only` | — | `DE exit` | direct | **не фиксирован на DE** (см. ниже) |

Важно:

- у всех текущих маршрутов **нет multi-candidate hop-ов**, поэтому
  per-hop `round`/`random` в админке сейчас фактически не работает;
- у профилей со включённым split-routing целевой трафик идёт максимум через
  **два** сервера;
- `DE only` — исключение: split выключен, поэтому он использует все три
  URL как fallback, но не фиксирует DE (см. ниже);
- третий сервер у split-профилей участвует только в фоновых poll-запросах.

### `DE only` — отдельный случай

У профиля `DE only` стоит `split_enabled = false`, но `route_non_ru = DE exit`.
При `routingEnabled = false` движок делает `SplitRouter.enabled = false`,
`route_for()` возвращает `("tunnel", None, ...)`, и entry выбирается
клиентским `server_selector` по всем `server_urls`.

То есть профиль **не гарантирует DE**; он может пойти на `ru-2`, `fi-1`
или `de-1` по кругу/случайно. Название вводит в заблуждение.

Если нужен настоящий «DE only», есть два варианта:

1. включить split routing и поставить `DE exit` и для RU, и для non-RU;
2. добавить в модель профиля отдельный «default route» / per-profile URL
   list, который используется при `split_enabled = false`.

## 5. Как распределяется цепочка

Ниже — распределение для трёх узлов `ru-2`, `de-1`, `fi-1` и одинаковых
списков кандидатов.

### 2 hop-а, `round`

Из-за запрета повторных узлов и синхронных счётчиков:

```
ru-2 -> de-1
de-1 -> fi-1
fi-1 -> ru-2
ru-2 -> de-1 ...
```

- 3 разные пары, не 6;
- в каждой сессии участвуют 2 сервера;
- каждый узел участвует в 2 из 3 пар (66.7%);
- все три сервера используются за 3 сессии;
- рисунок детерминированный и легко узнаваемый.

### 2 hop-а, `random`

Все 6 упорядоченных пар без повторов:

```
ru-2 -> de-1, ru-2 -> fi-1,
de-1 -> ru-2, de-1 -> fi-1,
fi-1 -> ru-2, fi-1 -> de-1
```

- в каждой сессии 2 сервера;
- за много сессий используются все 3;
- распределение равномернее по парам, но нет гарантии чередования.

### 3 hop-а, `round`

Три циклические перестановки:

```
ru-2 -> de-1 -> fi-1
de-1 -> fi-1 -> ru-2
fi-1 -> ru-2 -> de-1
```

- в каждой сессии участвуют **все три** сервера;
- но только 3 из 6 возможных перестановок;
- детерминированный цикл.

### 3 hop-а, `random`

Все 6 перестановок:

```
ru-2 -> de-1 -> fi-1
ru-2 -> fi-1 -> de-1
de-1 -> ru-2 -> fi-1
de-1 -> fi-1 -> ru-2
fi-1 -> ru-2 -> de-1
fi-1 -> de-1 -> ru-2
```

- в каждой сессии все три сервера;
- максимальное разнообразие;
- выше задержка (два relay-прыжка).

### Синхронизация `round`

Счётчики `round` живут внутри клиента и стартуют с нуля. После перезапуска
VPN все клиенты, подключившиеся одновременно, начнут с одной и той же пары
(например, `ru-2 -> de-1`). Это не глобальная балансировка, а локальная.
`random` такого эффекта не даёт.

## 6. Есть ли конфликт?

Прямого конфликта нет, но есть четыре проблемы понимания и конфигурации:

1. **Клиентский `URL select` выглядит как выбор маршрута, но при активном
   split-routing не влияет на entry.** Он остаётся только fallback-механизмом.
2. **Per-hop `round`/`random` в админке сейчас не влияет ни на что**, потому
   что у всех текущих hop-ов один кандидат.
3. **`split_enabled = false` отключает не только split, но и выбранный
   `route_non_ru`.** Профиль `DE only` из-за этого не фиксирует DE.
4. **Клиентские локальные маршруты имеют приоритет над профилем из
   подписки.** `apply_subscription()` сначала применяет `split_routing` из
   подписки, а затем перекрывает actions из `routing` (то, что пользователь
   выбрал в приложении). То есть пользователь может переопределить
   `route_ru`/`route_non_ru`, которые задал админ.

Дополнительно: Android при повторном импорте подписки обновит профили и
маршруты, но если профиль уже активен и приложение не переимпортировало
подписку, старые `route_ru`/`route_non_ru` могут остаться в локальном
конфиге.

### Влияние клиентского состояния URL

Стратегия hop-а выбирает только из **доступных** URL:

```
available = server_urls − disabled_urls − карантин
```

Поэтому клиентские настройки URL всё-таки влияют на маршрут:

- если пользователь снял галочку с URL, этот узел выпадает из кандидатов;
- если URL в карантине после ошибок, он тоже выпадает;
- если в hop-е остался один доступный кандидат, `round`/`random` становятся
  бессмысленными;
- если доступных кандидатов меньше числа hop-ов, цепочка сокращается.

Есть и пограничный случай: если **все** URL в карантине, `_pick_chain()`
сейчас откатывается к полному пулу кандидатов. Маршрут формально выбирается,
но poll-цикл затем закрывает сессии на недоступных URL. То есть при полном
карантине поведение ближе к «соединение не устанавливается», но причина в
логах выглядит как ошибка маршрута/URL, а не «нет доступных серверов».

## 7. Насколько это похоже на обычный веб-серфинг

Плюсы:

- клиент ходит на три разных URL, а не на один;
- пути выглядят как CDN-ассеты (`random_cdn_path`);
- фоновые пустые poll-запросы идут на все доступные URL, поэтому все
  серверы видят активность;
- сессия закрепляется за entry, как обычное TCP-соединение.

Минусы:

- сессия закреплена за entry/route на всё время жизни; это не ротация
  «на каждый HTTP-запрос»;
- фоновые poll-запросы очень регулярные. В Android `pollIntervalMs` по
  умолчанию **50 мс**, в desktop — 200 мс; jitter в Android 5 мс. При
  50 мс и трёх URL это до ~60 запросов/с, что не похоже на обычный браузер;
- пустой poll и poll с данными могут отличаться по размеру, поэтому
  активный entry можно попытаться выделить по объёму/таймингу;
- при 2-hop маршруте целевой трафик всё равно идёт через два сервера,
  третий получает только фоновые запросы;
- `round` детерминирован, а у всех клиентов стартует с одного индекса;
- во всех запросах используется один `X-Cid`, что позволяет коррелировать
  запросы между серверами.

## 8. Что делать, если цель — задействовать все три сервера

Нужны маршруты с несколькими кандидатами, а не один кандидат на hop.

### Вариант «RU exit, но entry распределён»

```
hop 1: [fi-1, de-1]   random
hop 2: [ru-2]         round
```

RU-трафик идёт либо `fi-1 -> ru-2`, либо `de-1 -> ru-2`. За сессию два
сервера, за много сессий — все три.

### Вариант «non-RU exit DE, entry распределён»

```
hop 1: [ru-2, fi-1]   random
hop 2: [de-1]         round
```

Аналогично: entry `ru-2` или `fi-1`, exit `de-1`.

### Вариант «полная сетка на 2 hop-а»

```
hop 1: [ru-2, de-1, fi-1]   random
hop 2: [de-1, fi-1, ru-2]   random
```

Все три сервера используются, но exit не фиксирован. Подходит, если
важнее разнообразие, а не конкретная страна выхода.

### Вариант «все три в каждой сессии»

```
hop 1: [ru-2, de-1, fi-1]   random
hop 2: [ru-2, de-1, fi-1]   random
hop 3: [ru-2, de-1, fi-1]   random
```

Каждая сессия проходит через все три узла; выше задержка. `round` даст
только 3 циклические перестановки, `random` — все 6.

## 9. Рекомендации

1. Переименовать в Android `URL select` в **Fallback URL select** или
   скрывать/деактивировать, когда активен маршрут со split-routing.
2. В админке показывать у hop-а предупреждение «один кандидат — стратегия
   не влияет на выбор».
3. Для профилей, где нужен фиксированный exit, использовать явные
   multi-candidate entry-маршруты (раздел 8).
4. Починить/уточнить семантику `split_enabled = false`: либо использовать
   `route_non_ru` как default route, либо явно писать в UI, что маршруты
   игнорируются и работает только `server_selector`.
5. Для симметричного распределения по всем трём серверам использовать
   `random`; `round` оставить для предсказуемой равномерности, понимая,
   что он синхронизирован между клиентами.
6. Если важна «обычность» трафика — увеличить и рандомизировать
   `poll_interval_ms`, уменьшить частоту фоновых пустых poll-ов или
   маскировать их размеры; текущие 50 мс в Android слишком регулярны.
7. Для 3-hop маршрутов помнить про задержку и лимит 3 hop-а.
