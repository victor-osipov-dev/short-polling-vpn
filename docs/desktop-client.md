# Desktop-клиент (Windows/Linux): профили, подписки, проверка

Desktop-клиент (`vpn_gui.py`) повторяет возможности Android-приложения:
несколько подписок, именованные профили с режимом и маршрутизацией,
живой статус URL и проверку реального подключения. Общий движок —
`tunnel.ClientTunnel`, тот же, что и в консольном клиенте (`main.py`).

## Запуск

Подготовка окружения (один раз):

```bash
uv venv .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.txt   # Windows
# или: python -m venv .venv && .venv/bin/pip install -r requirements.txt
```

Дальше:

- `start_vpn.bat` — графический клиент (окно + трей), берёт `.venv`, если он есть.
- `start_client.bat` — консольный клиент (`main.py`, без GUI), нужен `config.yaml` с `mode: client`.
- либо вручную: `.venv\Scripts\python.exe vpn_gui.py --config config.yaml`.

`config.yaml` не обязателен: если `profiles.json` ещё нет, профиль создаётся
из `config.yaml` (`DesktopConfig.seed_from_yaml`); без него профилей будет
ноль — добавьте подписку в UI. Настройки рабочего каталога:

- `profiles.json` — профили и подписки (модель совпадает с Android
  `ProxyConfig`/`VpnProfile`, поэтому подписки переносимы между устройствами);
- `desktop_prefs.json` — активный профиль и язык интерфейса.

Оба файла в `.gitignore`: они содержат `device_id` и данные подписок.

## Профили и подписки

- На главном экране профили сгруппированы по подписке. В заголовке группы:
  **Тест всех**, обновление подписки и удаление только этой подписки.
- Подписку можно добавить тремя способами: вставить URL, взять из буфера
  обмена или загрузить JSON из файла.
- id профиля = `sub:<slug>:<client_profile_id>`, где `slug` — UUID v3 от MD5
  ключа подписки. Формула совпадает с Android
  (`UUID.nameUUIDFromBytes(...).toString().take(8)`), поэтому повторный
  импорт обновляет профили, а не плодит дубликаты.
- `device_id` генерируется отдельно для каждой подписки и сохраняется при
  повторном импорте.
- Отключённые в подписке профили (`enabled: false`) не импортируются.
- Профили, исчезнувшие из свежего payload, удаляются только у своей
  подписки.

## Режимы

- **Proxy (SOCKS5)** — клиент поднимает SOCKS5 на `127.0.0.1:8888` и
  HTTP CONNECT на `127.0.0.1:8889` и **ставит системный прокси Windows** на
  HTTP-порт, поэтому браузер и обычные приложения сразу идут через туннель.
  Перед этим сохраняются прежние настройки прокси (например, v2rayN):
  на Disconnect они возвращаются, а не просто выключаются. Приложения,
  которые не уважают системный прокси, можно вручную направить на
  `socks5://127.0.0.1:8888`.
- **VPN (TUN)** — настоящий VPN: `bin/win/tun2proxy-bin.exe` создаёт
  Wintun-адаптер, заворачивает в него весь IPv4-трафик машины и отдаёт его
  локальному SOCKS5. Работает для любых приложений, включая те, что
  игнорируют системный прокси.
- **VPN (system proxy)** — старый вариант: выставляется системный прокси
  Windows (`ProxyServer = 127.0.0.1:<http_port>`). Трафик приложений,
  уважающих системные настройки, идёт через туннель; остальные — мимо.
  При остановке прежние настройки прокси возвращаются, а
  `_schedule_proxy_guard` периодически возвращает нашу настройку, если её
  перебили.

### Как устроен TUN-режим

1. TUN требует прав администратора. GUI **не** запускается elevated:
   при первом подключении он просит UAC и поднимает отдельный процесс
   `vpn_helper.py` (в `.exe`-сборке — тот же exe с флагом `--tun-helper`).
   Помощник слушает `127.0.0.1`, требует случайный токен и умеет только
   `start`/`stop`/`ping`/`quit`, поэтому дальше подключение/отключение
   идут без новых запросов UAC (соединение с помощником переиспользуется,
   а при закрытии приложения отправляется `quit`). Если приложение упало,
   помощник завершится сам через 15 минут простоя (`HELPER_IDLE_TIMEOUT`)
   и вернёт DNS.
2. Перед поднятием адаптера движок заранее резолвит имена узлов в IP.
   Это обязательно: после `--setup` весь трафик уходит в TUN, и наш
   собственный poll-запрос к серверу без этого зациклился бы.
3. Poll-запросы привязываются к IPv4 физического адаптера
   (`client.local_address`), а IP узлов попадают в `--bypass`. Оба
   механизма держат служебный трафик вне туннеля.
4. DNS: по умолчанию (`tun.dns_hijack`) резолвер физического адаптера
   переключается на шлюз TUN (`10.0.0.1`), а `--dns virtual` заставляет
   tun2proxy самому отвечать на DNS и передавать **имена** дальше в SOCKS5.
   Так имена не утекают провайдеру, а split-routing получает настоящий
   hostname. При остановке DNS возвращается (состояние хранится в
   `%TEMP%\vpnclient_dns_state.json`, поэтому восстанавливается даже после
   аварийного завершения).
5. По умолчанию адаптер называется `vpnclient` (`tun.name`), MTU 1500.

Настройки TUN — в **Настройки → Подключение**: MTU, имя адаптера, порт
помощника, дополнительный bypass, DNS-стратегия, переключатель перехвата
DNS, а также idle-timeout и DNS-релей.

`Disconnect` не блокирует интерфейс: остановка tun2proxy и восстановление
DNS (PowerShell) выполняются в фоновом потоке, кнопка показывает
«Отключение…», а окно продолжает отрисовываться.

Если `bin/win` отсутствует, TUN-режим помечается недоступным, и профиль
можно оставить на системном прокси.

## Раздельная маршрутизация

В настройках профиля (вкладка **Подключение**) для RU, non-RU и локальной
сети выбирается маршрут из каталога подписки или `direct`. Действия
профиля имеют приоритет над действиями подписки
(`connection_test._prepare_test_config`).

## Проверка подключения

Кнопка **Тест** у профиля и **Тест всех** у подписки проверяют реальное
подключение, а не ICMP:

1. `connection_test.test_profile` поднимает временный туннель с настройками
   профиля (маршруты берутся из снимка `nodes`/`routes`, без повторной
   загрузки подписки).
2. Через выбранный маршрут открывается сессия к `api.ipify.org:80`
   (fallback `ifconfig.me:80`).
3. UI показывает задержку, exit IP и фактическую цепочку узлов, например
   `ru-2 → de-1`.

Если маршрут невозможен (нет узлов, битая цепочка), тест показывает ошибку
маршрутизации, а не молчаливое переключение. Тесты идут последовательно и
не мешают запущенному VPN.

## Живой статус URL

Список серверных URL показывает состояние каждого адреса: **Активен**,
**Отключён** (чекбокс снят) или **Карантин · Ns**, плюс число ошибок.
Кнопка **Сбросить ошибки** (`ClientTunnel.reset_url_status`) обнуляет
счётчики и снимает карантин на лету. Снятие чекбокса сразу применяется к
работающему туннелю (`ClientTunnel.set_disabled_urls`).

## Ключи: подписка vs общий PSK

Если в конфиге есть `user.uuid` и `user.secret` из подписки, ключи
шифрования выводятся из секрета пользователя, а `security.psk` не
используется (он может быть пустым/плейсхолдером). Без per-user секрета
`security.psk` обязателен, иначе `ClientTunnel` падает с понятной ошибкой
`invalid security.psk ...`.
