# Отчёт: поведение VPN при нескольких `server_urls`

Дата: 2026-11-13
Серверы: `177.3.220.12:8443`, `2.27.37.211:8443`
Клиент: desktop `tunnel.py` / протокол short-polling

## 1. Как сейчас работает выбор URL

- URL выбирается заново на **каждый poll** (каждые ~200 мс) в `_pick_server_base()`.
- Один poll содержит кадры **всех** активных сессий и уходит ровно в один выбранный URL.
- Сервер хранит состояние TCP-сессий (`session_id`) только у себя. Второй сервер об этих сессиях не знает.
- Ответ приходит только от того сервера, который опрашивался.
- `server_selector`:
  - `round` — строгое чередование URL;
  - `random` — случайный URL на каждый poll.

## 2. Результаты экспериментов

| Сценарий | Успешных запросов | Комментарий |
|---|---|---|
| 1 сервер (база) | **7/7** | 6 × `example.com` + файл 300 КБ (скачан целиком) |
| 2 разных сервера, `round` | **0/7** | 0 байт; при этом оба сервера отвечают `200 OK` |
| 2 разных сервера, `random` | **4/7** | 300 КБ скачались, но 3 запроса упали |
| Один и тот же сервер указан дважды, `round` | **4/4** | Работает: состояние сессий общее |
| Хороший сервер + URL с HTTP 500, `round` | **1/4** | Битый URL опрошен 22 раза, 44 ошибки |
| Оба URL «битые» (HTTP 500) | 0 запросов пользователя | 29 poll за 6 с, 28 ошибок, 14 сбросов карантина |

Распределение poll-запросов:

- `round`: 187 запросов на `177.3.220.12`, 186 на `2.27.37.211`;
- `random`: 77 и 70 соответственно.

То есть при `round` оба сервера получают ровно половину запросов, но пользовательский трафик не работает вообще.

## 3. Почему `round` с двумя разными серверами даёт 0%

Пример одного HTTPS-соединения:

1. Poll №1 → сервер A: уходит `FLAG_NEW`, A открывает TCP-соединение к сайту.
2. Poll №2 → сервер B: уходит `FLAG_DATA` (первые байты TLS). B не знает такую сессию и **молча выбрасывает данные**.
3. Poll №3 → сервер A: уходит следующий `FLAG_DATA`, но A не получил предыдущие байты — TLS-рукопожатие не складывается.
4. Клиент получает ответы от A и B, оба отвечают `200`, счётчики успеха растут.

В логах обоих серверов это видно напрямую:

```
[WARNING] vpn-server: [server] DATA: session 66320be5 not found or closed
[WARNING] vpn-server: [server] DATA: session 35b4d48f not found or closed
```

Для пользователя: **VPN «подключён», индикатор зелёный, страницы не открываются**. Карантин не помогает, потому что оба сервера формально здоровы.

`random` иногда работает: случайно несколько poll подряд попадают в один сервер. Это лотерея, а не балансировка; чем длиннее соединение, тем выше шанс разрыва.

## 4. Важный нюанс про CDN

Несколько URL — это корректная схема, **если все они ведут на один и тот же origin** (разные CDN-домены перед одним сервером). Тогда состояние сессий общее, и `round`/`random` работают. Именно так, вероятно, были устроены `ai-box-cars.ru` + `begetcdn` + `twcstorage`.

Два **независимых** сервера (`177.3.220.12` и `2.27.37.211`) — это два разных хранилища сессий, поэтому одновременно они работать не могут.

## 5. Дополнительные найденные ошибки

### 5.1. Потеря кадров при неудачном poll

Кадры (`pending_new`, `outgoing`) удаляются из очередей **до** отправки. Если запрос не удался, они теряются без ретрая. Одна неудачная отправка может навсегда подвесить сессию.

Статус: **не исправлено**, требует переработки очередей вместе с per-session affinity.

### 5.2. Карантин не перевзводился

После истечения карантина ключ оставался в `_url_cooldown_until`, поэтому условие `url not in self._url_cooldown_until` больше никогда не выполнялось. Битый URL пробовался снова и снова, но заново в карантин не попадал.

Статус: **исправлено**.

### 5.3. Двойной счётчик ошибок

При HTTP 4xx/5xx `_mark_failure()` вызывался дважды: до `raise_for_status()` и в `except`. `fail_limit=3` фактически срабатывал после двух ошибок, а счётчик в интерфейсе был завышен.

Статус: **исправлено**.

### 5.4. Ретрай-шторм при полном отказе

Когда все URL были в карантине, `_available_urls()` сразу очищал карантин и ошибки и пробовал снова — каждые 200 мс.

Статус: **исправлено**: клиент ждёт истечения ближайшего карантина (до 30 с за раз), не сбрасывая состояние, и пишет предупреждение один раз.

### 5.5. Ложный `URL recovered` на каждом poll

`_mark_success()` писал «URL recovered» при каждом успешном poll, потому что после сброса счётчика снова создавал ключ `0`.

Статус: **исправлено** (ранее).

## 6. Что исправлено в коде

Файлы:

- `tunnel.py`;
- `android-vpn-proxy/app/src/main/python/proxy_engine.py`.

Изменения:

1. `_expire_quarantines()` — истёкшие карантины снимаются, счётчик ошибок сбрасывается, URL получает свежую попытку.
2. `_mark_failure()` — карантин перевзводится после истечения предыдущего.
3. `_available_urls()` — больше не сбрасывает все карантины при полном отказе.
4. `poll_loop()` — при всех URL в карантине ждёт истечения ближайшего (максимум 30 с), логирует один раз.
5. `_poll_once()` — HTTP-ошибка считается ровно один раз; при `>= 400` запрос завершается без повторного списания ошибки.
6. `_mark_success()` — «URL recovered» только при реальном восстановлении после ошибок/карантина.

Проверено тестами:

- карантин после `fail_limit`, истечение, свежая попытка, повторный карантин;
- HTTP 500 даёт ровно одну ошибку, а не две.

## 7. Выводы

1. Нельзя одновременно использовать несколько **независимых** серверов с текущей схемой выбора URL на каждый poll.
2. Несколько URL допустимы, если это разные входы в один origin (CDN).
3. Для настоящей балансировки между разными серверами нужна **per-session affinity**: сессия закрепляется за конкретным URL на всё время жизни, poll-цикл группирует кадры по URL.
4. Карантин и обработка ошибок должны работать на уровне URL, а не «сбрасывать всё» при полном отказе.
5. Отдельно требуется устойчивость к потере кадров при неудачном poll и корректный failover.

## 9. Этап 1: per-session affinity — реализовано

### 9.1. Что изменилось

- У `ClientSession` появилось поле `server_base` — входной URL, за которым закреплена TCP-сессия.
- При создании сессии URL выбирается один раз через `_pick_server_base()` (round/random, без карантинных URL).
- `_poll_once()` больше не делает один общий запрос: кадры группируются по `server_base`, на каждый URL отправляется отдельный poll.
- Все доступные URL опрашиваются каждый цикл, даже без исходящих кадров — это нужно, чтобы забирать буферизованные ответы.
- Смещение времени (`_time_offsets`) ведётся отдельно для каждого URL: часы серверов могут расходиться, общий offset ломал бы HMAC.
- Ошибка URL изолирована: закрываются только сессии, закреплённые за этим URL. Остальные серверы продолжают работать.
- `FIN` для принудительно закрытых сессий отправляется на тот URL, который владел сессией.
- При отключении/карантине URL его сессии явно закрываются, чтобы приложение переподключилось, а не висело.

Файлы: `tunnel.py`, `android-vpn-proxy/app/src/main/python/proxy_engine.py`.

### 9.2. Результаты после исправления

| Сценарий | Результат |
|---|---|
| 1 сервер | **6/6** |
| 2 сервера, `round` | **8/8**, сессии 4/4, poll 33/33 |
| 2 сервера, `random` | **8/8**, сессии 6/2, poll 34/34 |
| Хороший + битый URL, `fail_limit=2` | **8/8** (битый URL ушёл в карантин до назначения сессий) |
| Хороший + битый URL, `fail_limit=100` | **3/6**: упали только сессии, закреплённые за битым URL; они явно закрыты, healthy-сессии не затронуты |
| Android-движок, 2 сервера, 4 запуска | **4/4** в каждом запуске |

Логи серверов за 15 минут новых тестов:

- `DATA: session not found or closed` — **0** на обоих серверах;
- `NEW`: 163 на `177.3.220.12`, 25 на `2.27.37.211`.

То есть кадры больше не уходят «не на тот» сервер.

### 9.3. Ограничения текущего этапа

- Опрашиваются все доступные URL каждый цикл, а не только те, где есть активные сессии. Для 2–3 серверов это нормально, для десятков — потребуется оптимизация.
- Маршруты (entry → relay → exit) ещё не реализованы: пока каждый URL — самостоятельный exit.
- Идентификация пользователей ещё не реализована: используется общий PSK.
- При падении сервера его сессии сбрасываются (TCP нельзя перенести), приложение переподключается.

Следующий этап — идентификация пользователей (`docs/routing-design.md`, Этап 2), затем маршруты и relay (Этап 3).
