# Short Polling VPN 1.1.0 — основной клиент для Windows (`spvpn`)

Нативный клиент для ПК: тот же poll-протокол, шифрование, MAC, маршруты и
split-routing, что и в Android-приложении. Это единственный поддерживаемый
десктопный клиент — Electron-версия и старый Python-GUI удалены из репозитория.
Один бинарник без Python и Electron: по умолчанию открывается нативное окно,
CLI/TUI доступны через `--no-gui` / `run`.

- Сайт и прямая загрузка: <https://victor-osipov-dev.github.io/short-polling-vpn/>
- Релиз 1.1.0: <https://github.com/victor-osipov-dev/short-polling-vpn/releases/tag/v1.1.0>

Что умеет:

- **два режима**: Proxy (локальный SOCKS5 + системный прокси Windows) и VPN (TUN,
  весь трафик системы через туннель);
- подписки по URL, из файла или inline JSON (профили + маршруты + split-routing);
- выбор профиля, ручной режим (свои entry-URL), refresh подписок;
- relay-цепочки (2+ хопа), split-routing `ru` / `non_ru` / `private`;
- тест профиля и «Тест всех» (exit IP, задержка, фактический маршрут);
- карантин «мёртвых» URL с автоматическим возвратом в строй;
- статус, счётчики, журнал, URL-статусы;
- русский и английский интерфейс, тёмная тема, трей, автозапуск Windows.

## Системный VPN (TUN)

VPN-режим реализован нативно: `wintun.dll` (встроен в exe) + `smoltcp`.
Никакого sing-box sidecar нет. Трафик забирается через адаптер Wintun и
разбирается стеком TCP/IP внутри процесса:

- TCP-соединения уходят в туннель по правилам split-routing;
- UDP обрабатывается только для DNS (порт 53) встроенным прокси до upstream;
- QUIC и прочий UDP отбрасываются, приложения автоматически откатываются на TCP;
- домены из DNS-ответов (UDP и TCP) кэшируются по TTL, чтобы split-routing
  работал по именам;
- маршруты `0.0.0.0/1` и `128.0.0.0/1` направляются в TUN и удаляются при
  отключении (всегда с маской, чтобы не задеть физический default route);
- entry-серверы, upstream DNS и direct-назначения временно пинятся на физический
  шлюз, чтобы не было рекурсии; соединения к самим entry-серверам всегда идут
  напрямую, даже если пиннинг не удался;
- IPv6 в туннель не проксируется: его маршруты заводятся в TUN и отбрасываются,
  поэтому утечки IPv6 мимо VPN нет; IPv6-DNS не анонсируется;
- одновременно держится не больше 512 TUN-соединений;
- системный прокси не трогается в VPN-режиме.

Для создания адаптера и изменения маршрутов нужны **права администратора**.
Если приложение запущено без прав, VPN-режим вернёт ошибку, а окно предложит
«Перезапустить от администратора» (UAC). Proxy-режим работает без elevation.

## Сборка

```powershell
cd rust-client
cargo build --release
```

Бинарник: `target\release\spvpn.exe` (Linux/macOS — `target/release/spvpn`).
`wintun.dll` уже лежит в `resources/` и встраивается в exe; рядом с exe его
держать не обязательно.

Без GUI/TUN (лёгкая консольная сборка):

```powershell
cargo build --release --no-default-features --features tui
```

Только CLI, без интерактивного дашборда:

```powershell
cargo build --release --no-default-features
```

Требуется Rust 1.80+.

## Запуск

Двойной щелчок по `spvpn.exe` открывает окно. Флаги:

| Флаг | Что делает |
| --- | --- |
| `spvpn` | Открыть GUI |
| `spvpn --minimized` | Запустить свёрнутым в трей |
| `spvpn --no-gui` | Не открывать окно (CLI/TUI) |
| `spvpn run [--no-tui]` | Поднять туннель из консоли (режим из профиля) |
| `--dir <path>` | Каталог конфигурации (или `SPVPN_DIR`) |
| `-v/--verbose` | Подробный лог протокола |

В GUI: выберите профиль, режим **Прокси** или **VPN**, нажмите «Подключить».
Для Proxy-режима системный прокси включается автоматически (можно выключить в
настройках), для VPN — поднимается TUN.

Консольные режимы (`run` и TUI через `--no-gui`) используют тот же режим
активного профиля: Proxy поднимает SOCKS5, VPN поднимает TUN. Для VPN нужна
консоль с правами администратора; без них команда завершится понятной ошибкой.
Сборка `--no-default-features` не содержит TUN и в VPN-режиме сообщит об этом.

## Быстрый старт в консоли

```powershell
spvpn subs add "https://fimdi.ru/sub/<token>" --name main
spvpn profiles
spvpn use Relay
spvpn --no-gui          # интерактивный TUI-дашборд
```

В другом окне направьте приложение на SOCKS5 `127.0.0.1:8890` (по умолчанию).
Без дашборда:

```powershell
spvpn run --no-tui
```

В VPN-режиме запускайте из консоли администратора (или используйте GUI, который
сам предложит UAC-перезапуск).

## Команды

| Команда | Что делает |
| --- | --- |
| `spvpn` | GUI (окно) |
| `spvpn --no-gui` | TUI-дашборд на активном профиле |

| `spvpn test [profile] [--all] [--parallel N] [--target URL] [--json]` | Проверить связь: exit IP, задержка, маршрут (результаты выводятся по мере готовности) |

Примеры:

```powershell

spvpn config set disabled_urls "https://dead.example.com:8443"   # исключить узел из маршрутов
```

## Interface

Окно состоит из трёх разделов:

- **VPN** — статус, режим Proxy/VPN, кнопка подключения, статистика, профили и
  подписки, «Тест» / «Тест всех»;
- **Настройки** — язык, автозапуск, поведение окна и трея, системный прокси,
  параметры поллинга, Check URL, TUN (адрес, маска, DNS, MTU, upstream,
  исключения), split-routing, статусы entry-URL, управление подписками;
- **Логи** — хвост `spvpn.log`, кнопки обновления и открытия папки.

Закрытие окна по умолчанию сворачивает приложение в трей (отключается в
настройках). В трее есть «Открыть», «Подключить», «Отключить», «Выход».
Если трей недоступен, окно не скрывается, чтобы приложение не «потерялось».

## TUI

Запускается через `spvpn --no-gui`, если stdout и stdin — терминал. Если
подписок ещё нет, открывается экран приветствия с командами добавления
подписки и путём к каталогу конфигурации: `r` перечитывает конфиг, `q` — выход.

Клавиши:

- `q` / `Esc` / `Ctrl+C` — выход (терминал восстанавливается);
- `Tab` / `1` / `2` — вкладки Status / Logs;
- `j` / `k` (или стрелки) — прокрутка, `Home` — в начало, `g` — следить за логом.

На вкладке Status: uptime, активные сессии, поллы, трафик и скорости, split,
последняя ошибка, список URL с сессиями, ошибками и остатком карантина.

## Файлы и настройки

Каталог конфигурации: `%APPDATA%\spvpn` (Windows), `~/.config/spvpn` (Linux/macOS).
Переопределяется `--dir` или `SPVPN_DIR`.

- `config.json` — настройки, подписки, профили (секреты в открытом виде — это локальный файл);
- `state.json` — pid/socks/control работающего демона;
- `spvpn.log` — журнал;
- `cache/` — кэш geoip/domains;
- `wintun.dll` — извлекается рядом с конфигом при первом VPN-подключении.

Полезные ключи `config set`:

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `socks` | `127.0.0.1:8890` | адрес SOCKS5 |
| `http-listen` | `127.0.0.1:18889` | HTTP CONNECT-прокси для системного прокси Windows (`spvpn run --http ...`) |
| `control` | `127.0.0.1:8891` | локальный control API |
| `poll-ms` / `jitter-ms` | `200` / `5` | интервал поллов и джиттер |
| `idle-ms` / `min-ms` | `800` / `100` | адаптивный поллинг: простой и нижняя граница |
| `chunk` | `262144` | сколько байт забирать на сессию за полл |
| `frames` | `32` | максимум кадров в одном полле |
| `pad` | `true` | выравнивание размера запросов |
| `http2` | `true` | HTTP/2 к CDN |
| `verify-tls` | `true` | проверка сертификатов |
| `selector` | `random` | выбор entry-URL: `random` или `round` |
| `fail-limit` / `cooldown` | `3` / `60` | карантин URL: неудач до блокировки и пауза, с |
| `idle` | `0` (выкл.) | пауза трафиковых поллов после простоя, с |
| `urls` | — | ручные entry-URL (включает профиль `manual`) |
| `psk` | — | общий PSK, если в подписке нет per-user секрета |
| `check-url` | `https://www.cloudflare.com/cdn-cgi/trace` | цель для `spvpn test` |
| `poll-path` / `host-header` | `/poll` / — | путь полла и Host для CDN-режима |

Exit IP в `spvpn test` берётся из строки `ip=...` (Cloudflare trace), из голого
IP-адреса (ipify, ifconfig.me) или из JSON-поля `ip` / `query` / `origin`.
Тест считается проваленным, если IP не удалось распознать.

TUN-настройки (`tun-address`, `tun-netmask`, `tun-dns`, `tun-mtu`,
`tun-dns-upstream`, `tun-exclude`) редактируются в GUI и хранятся в `config.json`.
`tun-exclude` принимает IPv4-адреса и CIDR через запятую (`10.0.0.0/8`,
`192.168.1.5`); эти направления остаются на физическом шлюзе.

## Маршруты и split-routing

Профиль — это пара «подписка + маршрут». Идентификатор вида `<uuid>::<route-slug>`,
имя маршрута берётся из подписки. Split-routing (`ru`, `non_ru`, `private`) приходит
в подписке и применяется на клиенте: для каждой сессии выбирается цепочка hops
(например, `e1 -> x` или один `x`), а `X-Route` уходит на сервер только для цепочек длиннее
одного хопа. В GUI можно переопределить действия для активного профиля.

## Как это устроено

- Один воркер на пару `(entry URL, маршрут)`; сессии группируются, чтобы у каждого полла был
  единый `X-Route`.
- Кадры всех активных сессий пакуются в один запрос (до `frames` кадров), ответ читается
  стримом; после полла воркер не спит фиксированные 200 мс, а ждёт события (новые данные,
  новое соединение, EOF) с таймаутом — это снижает задержку первого байта.
- Ошибка URL закрывает только сессии этой группы, затем URL уходит в карантин и проверяется
  фоновым health-поллом. Если все узлы маршрута в карантине, используется рабочий узел из
  остальной подписки (в логе: `failing over`).
- Отключённый в GUI узел удаляется и из списка кандидатов маршрутов, а не только из пула URL.
- Обмен: HKDF-SHA256 + AES-256-GCM, HMAC-SHA256 по `client_id + user + device + route + ts + blob`.

## Производительность

На локальном стенде (два Python-реле, `max_chunk_bytes = 1 MB`) release-сборка даёт
**11.3 MiB/s** в один поток и 8.2 MiB/s на 20 параллельных загрузках (20/20 без ошибок,
проверка SHA-256 совпадает). Debug-сборка на том же стенде — около 1.5 MiB/s, поэтому
для реального использования собирайте `--release`. За полл сервер может вернуть несколько
мегабайт (наблюдалось 4.1 МБ). На реальных узлах скорость определяется CDN и каналом.

```powershell
cargo test                      # с GUI/TUN (включая отрисовку TUI)
```
